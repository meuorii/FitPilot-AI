# FitPilot AI Mobile — Phase 1 Audit

**Audit date:** 2026-11-14
**Scope:** read-only source inspection and planning documentation. No Expo app, package, screen, business-logic, database, or deployment changes were made.

## Executive assessment

The repository contains a functioning-looking Vite/React client, a separately packaged Express API, and a separately packaged FastAPI AI service. They share no root package workspace. The Express API already exposes most data required for a native client, including profile reads, date-based meals, progress logs, settings, coach context/chat, and recoverable workout sessions. The mobile client can therefore be an additional HTTPS bearer-token client while both clients share backend accounts and persisted records.

**Readiness: READY WITH CONDITIONS.** Phase 2 can start as an isolated SDK 54 shell after confirming SDK 54’s ongoing support horizon and choosing Android/iOS device access. Before auth release, address the verified default internal credential exposure through separately authorized operations; before feature phases, resolve the response and parser behavior gaps noted below. There is no evidence of a need to alter web or database behavior just to scaffold the mobile shell.

## Express API contract inventory

All routes mount at `https://fitpilot-api-rp3p.onrender.com/api/v1` in current web services. Authenticated route groups call `authenticateUser`, require `Authorization: Bearer <JWT>`, and return JSON. The standard success envelope is `{ success: true, data, message? }` but some success routes return only `{ reply }` or `{ success, message }`. Error shapes vary between `{ success:false, message, code?, data? }`, `{ success:false, error, message }`, and FastAPI-style detail errors. Do not treat frontend response interfaces as proof of actual response shape. A general `/api` IP limiter is configured at 100 requests / 15 minutes; no route-specific AI or verification limiter is present in the inspected Express app.

Contract source map: mounted paths are in `server/src/app.ts` and `server/src/routes/*.routes.ts`; request handling and actual response construction are in matching `server/src/controllers/*.controller.ts`; browser request serializers are in `client/src/services/api/*.ts`; declared payload/response interfaces are in `client/src/services/types/*.ts`. Use the latter as a client migration aid and reconcile against controllers. Across the API, observed success codes are generally 200 for reads/updates and 201 for creates; observed validation errors are 400, missing/invalid auth is 401, unverified login is 403, missing records 404, duplicate/conflict states 409, IP throttling 429, server errors 500, and verification email delivery errors 503. Each controller does not use every status, and exact status/body is route-specific as summarized below.

## Authentication and AI boundaries

- `server/src/controllers/auth.controller.ts` signs HS256 JWT access tokens with a **7-day** expiry. No refresh endpoint, refresh token, token rotation, session table, revocation list, or JWT blacklist was found. Logout in the web client deletes local/session storage only; server accepts a valid token until expiry.
- `server/src/middleware/auth.middleware.ts` checks signature/algorithm/expiry and extracts id/email. It does not query profile state or verify that an account has not since been disabled. `GET /profile/me` can validate a token and restore profile data, but cannot renew it.
- Register creates an unverified profile and sends email; token is not issued until email verification. Login rejects unverified accounts (403). Verified users can be onboarded or not; `user.is_onboarded` is included for route decisions. Current login web navigation ignores this field; mobile guard should route verified incomplete profiles to onboarding.
- Store the short-lived current access token using SecureStore, hydrate before any protected redirect, send only as Bearer over HTTPS, clear on explicit logout and definitive 401, preserve drafts on transient failures, and avoid caching token in Zustand/AsyncStorage/query cache. Session persistence beyond seven days requires a new backend refresh design; do not pretend the current API supports indefinite sessions. SecureStore protects at-rest credentials but does not make a stolen valid bearer unusable.
- Verification code: six digits, SHA-256 hashed in DB, 10-minute expiry, timing-safe comparison. The only inspected Express limit is broad per-IP 100/15 minutes for all `/api` calls; verification/login/AI do not have an observed narrower route-specific budget or account attempt lockout. Consider dedicated auth and expensive-AI throttles as backend hardening.
- Request chain: authenticated mobile → Express `POST /meals/parse-ai`, `/coach/chat`, etc. → Axios AI client with 30-second timeout and internal header → FastAPI `/api/v1/ai/{parse-meal,parse-workout,coach-chat}` guarded by required internal header → Pydantic response models → OpenAI-compatible Qwen provider. The Python service must remain private; mobile must never embed its key or call it directly.
- Legacy meal parse path `/meals/parse-ai` uses internal Qwen; `/meals/parse` is a separate layered parser (table → local food DB → LLM fallback/manual) and is the route currently documented in `meal.ts` as smart parse. Preserve both until all web/mobile callers are audited; ensure AI suggestions are shown for correction and the user explicitly confirms before `/log` or `/log/batch` persistence.
- AI service uses configured inference endpoint/model and JSON structured output for meal/workout; Pydantic response models validate output. Qwen provider has no explicit retry/backoff in inspected code; Axios timeout is 30 seconds; no explicit OpenAI timeout/retry options, circuit breaker, or inference rate limit observed. FastAPI coach route moves sync inference to a worker thread. Health endpoints and `/docs`/`/redoc` are public by default; Express health includes configured AI service endpoint. Review exposure as deployment hardening.

## Security and reliability findings

| Severity | Finding | Evidence and recommended action |
|---|---|---|
| **High — verified** | Same hardcoded fallback internal key exists in `server/src/config/env.ts` and `ai-service/app/core/config.py`. SDK 54 is therefore the newest SDK that can target App Store Expo Go on iPhone, but a compatible Android build must be selected/downloaded for SDK 54. The machine has no `adb`; no SDK 54 Expo Go install, emulator, iPhone, or LAN/tunnel pairing was confirmed. iOS Simulator requires macOS/Xcode; Windows testing must use physical iPhone with the compatible Expo Go or an agreed remote/macOS path. Expo docs caution that production-quality feature parity and custom app links/native config need development builds; Expo Go cannot include app-specific native identifiers and remote push testing is not supported there.

| Feature | Expo Go classification |
|---|---|

| HealthKit / Health Connect | Development build and platform permissions/configuration likely required; deferred. |
| Custom native modules or app-specific universal links | Development build required. Standard Expo Router internal/deep links can be tried in Go, but ownership-verified app/universal-link association needs app build config. |
| Standard screens, forms, fetch, cached queries, bundled art, haptics/secure store | SDK 54 Go compatible with compatible SDK-bundled modules; validate on actual target devices. |
